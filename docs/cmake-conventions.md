# Code4hep CMake conventions

## TL;DR

- **Plain CMake is always first-class.** You can build any Code4hep package with
  standard `add_library` / `target_link_libraries` / `install` and it will work.
- The **`c4h_*` functions are optional convenience wrappers.** They expand to
  ordinary CMake and emit ordinary targets; you can mix them with plain CMake,
  ignore them, or drop down to plain CMake for any target that needs something
  they don't offer.
- They exist mainly to (a) remove repeated boilerplate and (b) let the automatic
  SCRAM→CMake converter emit compact, uniform files during the migration.

## Status of the `c4h_*` helpers

Every `c4h_*` function in `cmake/Code4hepBuildFunctions.cmake` carries a
`≡ PLAIN CMAKE` block in its header showing the exact standard-CMake commands it
expands to. Read that block if you ever want to know precisely what a call does,
or to convert a call back to plain CMake by hand.

There are only **two** behaviors in the helpers that a CMake-literate developer
cannot predict from CMake knowledge alone; both are deliberate and documented
below under [The one idiom worth learning](#the-one-idiom-worth-learning):

1. the `DEPS` "Subsystem/Package" shorthand, and
2. `find_package()` being auto-triggered by an `EXT_DEPS` namespace.

Everything else the helpers do — globbing `src/*.cc`, the install/export rules,
`VERSION`/`SOVERSION`, `-Wl,--no-undefined`, the ROOT-dictionary auto-detect,
plugin wiring — is plain project policy you could write by hand.

## Which to use

### Migrated packages (converter output)
Files generated by `tools/buildfile_to_cmake.py` use the `c4h_*` form. **Leave
them as-is**; do not hand-rewrite working generated files just to change style.
Re-running the converter regenerates them.

### New packages — your choice
- Reach for **`c4h_add_library(...)`** (and friends) for the common case: a
  shared library built from `src/*.cc`, public headers from `*.h`, linked
  against some dependencies, installed with the standard export set. This is the
  project's blessed shortcut and keeps new packages consistent with migrated
  ones.
- Use **plain `add_library(...)`** whenever you want full control or an
  unusual shape: `STATIC` / `OBJECT` / `INTERFACE` libraries, a non-standard
  source layout, `PRIVATE` vs `PUBLIC` dependency distinctions, per-target
  compile options, generated sources, etc. This is fully supported and requires
  no special blessing.

Both forms interoperate: a `c4h_add_library` target can depend on a plain
`add_library` target and vice versa, in the same build.

> **Direction of travel:** once the SCRAM migration is complete, new development
> is expected to lean on standard CMake practice. The helpers remain available
> and recommended for the common case, but they are a convenience, not a
> requirement, and no new code is obligated to use them.

## The one idiom worth learning

### `DEPS` shorthand
`DEPS` (and the plugin/executable/test equivalents) accept a
`Subsystem/Package` shorthand that resolves to the correct **namespaced** target
across the Stitched / Code4hep / experiment-specific repos. For example:

| You write        | Resolves to (build tree)                     | Resolves to (installed)        |
|------------------|----------------------------------------------|--------------------------------|
| `FWCore/Utilities` | `Stitched::stitched_FWCore_Utilities`      | same                           |
| `Code4hep/PodioUtilities` | `PodioUtilities` (bare in-tree target) | `Code4hep::PodioUtilities`     |

Plain CMake has no portable way to express "the right namespace depending on
which repo provides this" — that is exactly the gap the shorthand fills. In
plain CMake you would link the resolved target directly, e.g.
`target_link_libraries(MyLib PUBLIC Stitched::stitched_FWCore_Utilities)`.

To see how a shorthand resolves in your build, read the function's `≡ PLAIN
CMAKE` block or run `cmake --trace-expand` and look for the
`target_link_libraries` line.

### `EXT_DEPS` auto-`find_package()`
`EXT_DEPS` takes **fully-qualified imported targets** (e.g. `podio::podio`,
`ROOT::Core`, `Catch2::Catch2`). As a convenience, naming such a target also
triggers the matching `find_package()` for its namespace (with the right
`CONFIG`/component arguments — see the override table at the top of
`Code4hepBuildFunctions.cmake`). In plain CMake you would call `find_package`
yourself before linking the target. If you prefer that explicitness, you can:
call `find_package(...)` yourself and pass the targets via plain
`target_link_libraries` instead of `EXT_DEPS`.

## Subdirectory descent is explicit

The helpers do **not** automatically descend into subdirectories. Each
`CMakeLists.txt` that has child package directories must say so, with either:

```cmake
add_subdirectory(plugins)        # plain CMake — preferred when the set is fixed
add_subdirectory(test)
```

or the convenience equivalent:

```cmake
c4h_auto_subdirectories()        # add_subdirectory() for every child with a CMakeLists.txt
```

(Earlier versions descended automatically as a side effect of any `c4h_add_*`
call. That implicit behavior was removed precisely because it was invisible in
the file; descent is now always written out.)

## Escape hatches (mix freely)

- **Need PRIVATE deps, extra include dirs, raw `-l` flags, or compile options?**
  Call `c4h_add_library(...)` (or `add_executable`, etc.) then run the
  corresponding `target_*()` command on the resulting target. The target name is
  the `NAME` you passed, or the directory-derived name (see
  `_c4h_derive_target_name` in `Code4hepBuildFunctions.cmake`); plugins are
  `plugin_<name>`, executables `bin_<name>`.

  ```cmake
  c4h_add_library(DEPS FWCore/Utilities)        # target: <dir-derived name>, e.g. MyLib
  target_link_libraries(MyLib PRIVATE SomeThing::Private)
  target_compile_options(MyLib PRIVATE -funroll-loops)
  ```

- **Need a non-shared or otherwise non-standard target?** Skip the wrapper and
  use plain `add_library()` / `add_executable()`. Remember the project
  conventions the wrapper would have applied if you want them (install + export
  set, `FILE_SET HEADERS`, `VERSION`/`SOVERSION`, `-Wl,--no-undefined`); copy
  them from the function's `≡ PLAIN CMAKE` block.

- **Need a Debug or instrumented build?** Configure with
  `cmake -DCMAKE_BUILD_TYPE=Debug` (or `-DCMAKE_CXX_FLAGS=...`) rather than
  baking per-target flags into the wrappers.

## Where things live

- `cmake/Code4hepBuildFunctions.cmake` — the helper functions, each with its
  `≡ PLAIN CMAKE` expansion in the header.
- `tools/buildfile_to_cmake.py` — the SCRAM→CMake converter that emits the
  `c4h_*` calls for migrated packages.
- `stitched_issues.md` — upstream Stitched problems Code4hep works around.
